## Решение круга: гибрид C

**Формула (каноническая, словами пользователя, уточнена peer-4): «каждый
плагин знает, как и что ему читать; воркер остаётся API-агностик и работает
с верхним уровнем» — worker не знает форматов; он исполняет plugin-owned
operation, заранее статически собранную в его entry.**

Операция декларативна на уровне ПРОТОКОЛА (имена операций — один шаблон
entry для всех плагинов); исполняемый parser-модуль статически включён в
per-plugin worker-entry; runtime знает только lifecycle/transport и
op-envelope. Один универсальный worker без per-plugin bundle — невозможен
(функции/модули не пересылаются postMessage; import-map воркеру не
наследуется; external-RPC переносит ВЫЗОВ, не КОД — механика и отклонённые
обходы разобраны в переписке круга, mail-2138).

Не один универсальный worker-процесс на все форматы — один и тот же
runtime-код, инстанцируемый фабрикой плагина
(peer-4, вердикт; обе линзы сошлись на основании карт peer-5).

Отклонённые альтернативы (кратко, с причинами):
- (A) host-worker с реестром парсеров — требует manifest/worker-URL/CSP-шов
  и ломается об external-realm; самый дорогой DI/API; не первый шаг;
- (B) полностью отдельные воркеры ×4 — размножает lifecycle/протокол/тесты;
  изоляция не покупает ничего, чего не даёт C.

## Контракт: двухэтажный, оба этажа уже существуют (peer-1)

«Контракт НЕ создаётся — расширяется готовый двухэтажный слой»:

- НИЖНИЙ этаж (per-plugin, едет в воркер): байты → turns; правда формата —
  в модуле. Вход: ФАЙЛ ЦЕЛИКОМ (bounded) — один запрос, один файл, один
  ответ; чанкинг/streaming — ОПЦИЯ РЕАЛИЗАЦИИ stateless-модулей
  (claude/codex), НЕ обещание контракта (kimi stateful-flush, opencode join
  не переживают чанкинг). ВЫХОД: turns — упорядоченный список {role,text};
  summary|title — ПОБОЧНЫЙ ПРОДУКТ ОДНОГО прохода (не второй вход);
  у opencode честно ИНАЧЕ: summary/title приходят из session-строки
  SQL-запросом describe (отдельный запрос, не побочный продукт разбора) —
  adapter обещает turns из rows, а не summary из rows. Отказ — три рода, каждый назван как себя:
  (а) малый формат: строка без JSON / чужая форма пропускается МОЛЧА —
  знание о пропусках живёт в модуле (мутация чистоты застережена);
  (б) большой формат: файл, который модуль не может разобрать целиком,
  называет ПРИЧИНУ одной строкой — воркер не решает за плагин;
  (в) лимит: сообщение сверх bounded-потолка отклоняется ДО чтения тела —
  отказ транспорта, не формата.
- ВЕРХНИЙ этаж (общий, НЕ переезжает): parts→text, turns→title —
  packages/plugin-api/src/context/historyText.ts; прецедент дрейфа в его
  шапке — сам род «второй мозг», который слой уже однажды убил.

## Runtime (общий, format-agnostic — peer-4)

HistoryWorkerRuntime, один на приложение: bounded batches; request/generation;
stale-response suppression; dispose; transfer/clone policy. Живёт переживая
сканы и батчи; dispose — только с приложением. Generation-guard — правда
ЗАПРОСА, не воркера. Очередь внутри воркера хосту не видна; bounded-лимит —
единственный разговор о нагрузке.

## Погрузка модулей (реалистичность — peer-4)

Worker-entry, который бандлер видит СТАТИЧЕСКИ:
`new Worker(new URL("./history.worker.ts", import.meta.url), {type:"module"})`;
в entry — статический импорт общего runtime + парсер данного плагина.
ВЫЧИСЛЕННЫЙ import(url) из pluginManager — НЕ рабочий шов (manifest/CSP).
Фабрика `createParserWorker` инжектируется в claudeHistory/codexHistory/
kimiHistory/opencodeHistory (DI); в юнит-тестах — fake MessagePort.

## По плагинам (карты peer-5)

- claude: parseTurns stateless per-line; describe имеет ВТОРОЙ вход
  (sessions-index + precedence) — остаётся оркестрацией в main;
- codex: parseRollout stateless per-line, head 256KB;
- kimi: parseWire STATEFUL (flush на границе строк) — только целиком;
- opencode: sqlite-rows adapter поверх того же runtime; SQL остаётся в main
  (capability не воркера); строки не transferable — structured clone, честно
  НЕ называть zero-copy; bounded-порции строк, существующие LIMIT 20000 /
  cap 2MB сохраняются; UTF-8-буферы как опция — ТОЛЬКО после замера.

## Границы (ссылками)

- transcript-перечитывание на каждый клик — главный остаточный налог,
  воркер НЕ снимает; кэш turns — вопрос пользователю ПОСЛЕ замера
  (подробность — в task-носителе);
- external-плагины: их парс уже в iframe-realm (не главный поток);
  host-worker НЕ импортирует чужой realm; их собственные worker'ы —
  отдельный будущий шов (manifest capability/CSP);
- IO остаётся в main у всех: «main читает → воркер парсит → main получает
  turns» покрывает всех built-in;
- rust-diff 0.

## Цена швов (для постановки)

Runtime/протокол тестируется ОДИН раз (roundtrip, bounded, generations,
dispose — четыре падающих сторожа из task-носителя); у каждого JSONL-плагина
— golden fixtures + worker-entry тест; opencode — row-adapter/byte-cap тесты.
Бандл: по entry на формат, runtime не копируется.
