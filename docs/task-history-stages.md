## СТУПЕНЬ 1 — ЧЕСТНОСТЬ ЧТЕНИЯ (слова + контракт + точечная механика;
оценка после проработа: НЕ «дни слов» — Rust в двух пунктах, смена типа

Ничего не ускоряется — перестаёт лгать:

1. TRUNCATED-ЧИТАТЕЛЬ (ДВУХУРОВНЕВАЯ метка): FsFile.truncated ездит по
   IPC и не читается НИ ОДНИМ из трёх JSONL history.ts (claude/codex/kimi
   — все читают `file.text ?? ""`; читатели за пределами history.ts —
   FileViewer, kimi fork — их НЕ трогаем). Поведение хвостов РАЗНОЕ и
   это суть: claude/codex — рваная строка → continue, хвостовой ход
   ПРОПАДАЕТ (метка возможна только на СЕССИИ); kimi — накопленные
   фрагменты выливаются flush'ем в ОБЫЧНЫЙ ход, который молча
   укорачивается и выглядит целым (метка на СЕССИИ и на ХВОСТОВОМ
   TURN-е обязательна). ПРАВИЛО КАКОГО ЧТЕНИЯ: обрезание head/индексного
   чтения — НОРМА (ограничено нарочно, разговор не теряется) и НЕ
   помечается; помечается ТОЛЬКО обрезание чтения ТЕЛА, при котором
   теряется разговор — иначе флаг горит почти всегда (всякая сессия
   крупнее 64KB head-обрезана), несёт ноль информации и приучает не
   смотреть: шумная ложь вместо молчаливой (род: читатель без
   содержания). Названное = видимое: (а) поле контракта в Facts —
   про ТЕЛО-чтение; (б) метка в просмотрщике на сессии; (в) для kimi —
   на хвостовом turn-е (исполнимо ТОЛЬКО после пункта 6: сегодня
   AgentTranscriptEntry = {role, text}, места под метку нет — (в) не
   требовать раньше 6). Молчаливая потеря хвоста запрещена. Свидетель:
   мутация «снять читателя В history.ts» → тест красный — для этого
   добавляется ПАРНАЯ ветка truncated:true (все фикстуры сегодня
   false, torn-line-в-середине и torn-line-на-обрезанном-хвосте
   различимы ТОЛЬКО по флагу; старые torn-тесты остаются зелёными —
   они про середину). KIMI-ТОЧНОСТЬ подозрения (иначе свидетель всегда
   красный или всегда зелёный): хвостовой ход подозрителен ⟺
   truncated === true И последний ход родился из ФИНАЛЬНОГО flush'а —
   хвост файла это context.append_loop_event, а не завершённый
   context.append_message; если обрыв пришёлся на завершённое
   сообщение, финальный flush пуст, подозрительного хода НЕТ, потеря
   идёт целыми записями как у claude/codex. CODEX-ТОЧНОСТЬ (голова):
   describe читает голову 256KB (:151), заголовок (:169) выводится из
   обрезанного текста и выглядит целым — тот же род, что kimi-flush
   (тихая неполнота под видом полноты). ЛЕЧЕНИЕ — ПУНКТ 4 (семья
   названных исключений), НЕ здесь: фолбэка телу в codex-describe НЕТ
   и строить его нельзя — голова 256KB обрезана у большинства сессий
   (средний корпус 1.2MB), «фолбэк» стал бы нормой и замедлил бы скан
   в разы — регрессия на горячем пути вопреки «ничего не ускоряется»;
   род: правило-помечай-обрезанное применено там, где обрезание —
   НОРМА (похоронено в правиле какого чтения, не воскрешать).
2. ГРАНИЦЫ ЧТЕНИЯ НАЗВАНЫ В ОДНОМ МЕСТЕ: потолков ТРИ, назначение

## СТУПЕНЬ 2 — ДЕШЁВЫЕ МЕХАНИКИ (дни, без воркера)

1. ДВОЙНОЙ РАЗБОР УМИРАЕТ (№8): в fallback-пути claude describe+content =
   ДВА полных 8MB-чтения и ДВА parseTurns одного ref в одной BATCH-порции.
   Форма (peer-4): один combined-проход на fingerprint → turns+content+
   summary; title ВЫБИРАЕТСЯ В ПРЕЖНЕМ ПОРЯДКЕ (sessions-index >
   transcript-summary > first-turn) — precedence НЕ меняется, публичный
   describe не лжёт об источнике. Род: одна работа дважды.
2. REFRESH-ШТОРМ (№9): каждый бамп revision (батчи ×16 → сотни на первом
   скане) → refresh ОБЕИХ полос с atLeast=rows.length (глубина 300 → до
   600 строк перезапроса на каждый бамп). ШОВ ЛЕЧЕНИЯ — browser-level
   coalescer (useSessionsBrowser), НЕ manager (его публикуемый прогресс —
   чужие подписчики); throttle-окно + flush на scanning→false; вариант
   «один refresh на scan» — ПОЛЬЗОВАТЕЛЬСКИЙ выбор (incremental vs final),
   не молчаливый.
3. VIEWER-ОКНО (№7): SessionViewer рендерит ВСЕ загруженные turns дивами
   (тысячи нод на большой беседе). Форма: НЕ перенос useSessionListWindow
   (другая семантика); обобщение useScrollPaging + сохранение сторожей
   (stale-target, page-zero fallback, no-duplicate, short-page exhaustion).
4. IPC-ВЕЕР ЛИСТИНГА (kimi 2N readDir) — кандидат в ту же ступень по
   cheapness; механику назначит peer-4 при исполнении.

## ИНДЕКС-БЮДЖЕТ (№4) — вне трёх ступеней, режим измерения

Eviction НЕ первой ступенью (peer-4): FTS5 DELETE не освобождает файл
мгновенно; metadata обязан жить (пустой поиск/счётчики); молчаливое
выбрасывание content — изменение coverage, требующее честного поля.
Режим: измерить DB bytes / upsert-delete cost / search p95 на реальном
корпусе → пользователю варианты бюджета (mtime/LRU/content-only) с ценой
и изменением coverage.
