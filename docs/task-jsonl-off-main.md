## Политика чтения — пара воркеру (ВЫДЕРЖКА; исполнимый счёт ступени 1 — docs/task-history-stages.md, этот раздел справочный)

Правило: «размер сессии — не константа, а ДАННЫЕ; каждый путь чтения
называет, что ему нужно, и просит ровно это». Константа-8MB умирает
как класс.

- TRUNCATED-ЧИТАТЕЛЬ — ДО переноса в воркер: maxBytes ставит truncated,
  но ни один из ТРЁХ JSONL history.ts (claude/codex/kimi) флаг не читает
  — читатели есть в FileViewer и kimi fork, их не трогаем
  (обещание-флаг без читателя); обрезанное чтение называется обрезанным
  — молчаливая потеря хвоста запрещена (мутация чистоты: снять читателя
  В history.ts → тест красный);
- CONTENT-ДЛЯ-ИНДЕКСА ≠ TRANSCRIPT-ДЛЯ-ЧТЕНИЯ: индексу нужны факты
  (offset/len вхождений), не текст; describe-fallback (8MB) — явно
  названное исключение, не молчаливый дефолт; fast-дорожки (head +
  sessions-index) — норма;
- операции/ответы несут incomplete/truncated-семантику в контракте.

## Ступень 2 — range-чтение (ВЫДЕРЖКА; исполнимый счёт ступени 2 — docs/task-history-stages.md, этот раздел справочный)

«Страница 50 ходов не читает 121 MB» — ПОЛЬЗОВАТЕЛЬСКОЕ СВОЙСТВО, не
оптимизация; требует range поверх project_fs (сегодня чтение только от
начала): расширение команды offset/length + file identity (size/mtime)
против склейки версий; raw bytes (String ломается на UTF-8 границах);
worker-кэш с PARSER-EMITTED byte ranges (границы ходов называет парсер —
у kimi turn-boundary != line-boundary; SQLite-пары stateful не решают).
Первый проход индекса НЕ обещает O(page) — префикс до страницы назван
честно; read-with-slack — только переходный fallback ранних страниц.
Stream-handle — НЕ решено кругом: вариант выносится пользователю с ценой
(peer-4 оценил дороже range). SQLite-offsets — ОТКЛОНЕНО пользователем
(2026-08-22: «чтение через offset в DB — хуета»).

Обязательные оговорки (замер, все СЕМЬ обязательны):
- bounded-батчи — никакого 297-MB postMessage одним куском;
- transferable ArrayBuffer вместо гигантской строки;
- stale-generation guard и dispose воркера;
- замер до/после на тех же нагрузках — в отчёт числами;
- worker-инфраструктура в проекте отсутствует — новый шов бандла/тестов,
  заложить время на него, не на «просто перенести функцию»;
- OWNERSHIP/BACKPRESSURE: после передачи main НЕ хранит текст; очередь
  worker — hard capacity 1–2 файла (или явный байтовый бюджет); stale/
  dispose очищают queued payloads; BATCH=16 — размер индексной порции,
  НЕ число parser-payloads in flight; следующий файл читается только
  после выдачи слота;
- ИЗМЕРЯЕМЫЙ MEMORY CAP: bounded per-file/per-message + bounded in-flight
  bytes; проверка peak heap / worker heap — не только wall-time
  (критично для 60/297 MB скана).

Комментарий parseTurns о семантике формата (какие строки пропускаются,
почему) едет с кодом или умирает с ним — правда формата не разделяется
между файлами.

## Обнаружено картой (не этот заход, не молчим)

- transcript() перечитывает и перепарсивает до 8 MiB на каждый
  пейджинг-клик — постоянный налог просмотра, не разовый догруз. Воркер
  снимает CPU-половину, перечитывание остаётся. Кэш turns — отдельный
  вопрос пользователю ПОСЛЕ замера до/после.
- У четырёх источников «текст → turns» — общая точка. Задел-резерв, не
  шаг этого захода. opencode — в скоупе по слову пользователя (см. выше).

## Свидетели и мутации

- Свидетель №1: замер до/после — ДИАГНОСТИКА и свидетель вместе; метод
  обязателен: один build/browser/corpus; cold/warm явно; 3–5 повторов,
  median + range/p95; метрики симметрично для обеих нагрузок (60/297 MB
  scan и один фиксированный transcript-клик): main-thread long-task /
  максимальный frame gap + wall time до результата; для scan дополнительно
  число/эквивалентность проиндексированных строк (worker не теряет и не
  удваивает). Одна цифра одного прогона выводом не считается.
- Свидетель-инфраструктуры: тест воркер-шва — roundtrip; bounded-проверка
  (сверхлимитное сообщение отклоняется, не копится); ГЕНЕРАЦИИ: поздний
  ответ старой генерации НЕ применяется после нового запроса; DISPOSE:
  после dispose поздний ответ не меняет состояние и воркер не остаётся
  жив. Все четыре сценария — падающие сторожа, не обещания в тексте.
- Мутация приёмки (ДЕТЕРМИНИРОВАННАЯ, не по производительности):
  worker-adapter/production-path тест краснеет, если parseTurns вызван
  напрямую в main realm — forbidden main-parser spy/guard или явная
  DI-сем, которую bypass-мутант обходит. Замер деградации — поддержка,
  не критерий; compile-fail не зачёт.
- Мутация чистоты: изменить одну строку семантики (например, пропуск
  не-JSON строк) в воркер-версии — тест формата красный; тест обязан
  гонять РЕАЛЬНЫЙ воркер-парсер, не дублированную функцию.

## Форма отчёта

База «чисто ДО» с числами; оба замера числами с методом (повторы/
